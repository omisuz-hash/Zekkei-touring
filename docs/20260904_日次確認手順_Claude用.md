# 日次確認手順（Claude 用）

作成日: 2026-09-04
目的: Mac mini 上で毎朝 03:00（JST）に自動実行されるシード収集の結果を、Claude が毎朝確認・修正し、Omi に報告する
実行者: 毎朝 07:30（JST）に起動する Claude のルーティン（定期実行）

---

## 0. 前提

- リポジトリ: `omisuz-hash/Zekkei-touring`、作業ブランチ `claude/bike-touring-scenic-routes-et90o8`
- Mac 側の実行スクリプト `tools/seedpipeline/20260904_run_daily.sh` は、開始時に `git pull --ff-only` でこのブランチを取り込み、終了時に結果（`tools/seedpipeline/out/*.md, *.geojson, *.sql`）を `シード自動収集 YYYY-MM-DD` というコミットで push する
- したがって Claude がこのブランチに push した修正は、翌朝の実行で自動反映される
- Mac 側のログ（`out/logs/`）は push されない。ログが必要なときは Omi に依頼する
- 設計・運用の全体は `docs/20260904_シード自動収集パイプライン.md`

- 2026-09-05 以降、Mac の日次実行は結果 push のあとに Supabase へも自動で流し込む（`tools/supabase/20260905_db_admin.py seed`）。Supabase 側の件数はレポートには出ないため、必要なら Omi に `python3 tools/supabase/20260905_db_admin.py stats` の実行を依頼する

## 1. 確認手順

```bash
git fetch origin claude/bike-touring-scenic-routes-et90o8
git checkout claude/bike-touring-scenic-routes-et90o8
git pull --ff-only
git log --oneline -n 5                       # 「シード自動収集 <今日の日付>」があるか
cat tools/seedpipeline/out/*_seed_report.md  # 集計と道の一覧
```

確認する項目:

1. **実行の有無**: 当日（JST）の「シード自動収集」コミットがあるか。無ければ Mac 側で止まっている（スリープ、git 認証、コード障害のいずれか）。前日のコミットの有無も見て、いつから止まっているかを把握する
2. **集計の推移**: `videos_extracted`、`roads_ok`、`roads_suspect`、`roads_failed`、`videos_skipped` を前日と比較する。抽出した動画が増えているのに道が増えていなければ抽出の問題。要確認・失敗の比率が 3 割を超えていれば形状づけの問題
3. **道の一覧の目視**（言及数上位 20 本程度）: 名前が道として妥当か、区間（始点〜終点）が道の実態に合うか、距離が常識的か（通称で呼ばれる道は 2〜80km が普通）。ゴミの典型: 帰り道の国道、市街地の移動区間、施設名だけの「道」、明らかに別の場所に飛んだ区間
4. **GeoJSON**: 必要なら `python3` で座標の外接矩形を出し、都道府県と整合するかを確認する（地図を見る手段が無いため数値で判断）
5. **SQL**: 出力本数と、`insert into public.zekkei_roads` の件数が一致しているか
6. **スポット**: `spots_total` が増えているか、`roads_spots_pending` が減っているか。写真は `spots_with_photo` の比率（展望台・峠・道の駅で 5 割前後が目安）。スポット名が施設名として妥当か（「絶景」「山」だけのような一般語は Gemini の抽出精度低下の兆候）

## 2. よくある問題と対処

| 症状 | 原因の候補 | 対処 |
|---|---|---|
| 当日のコミットが無い | Mac がスリープ / git push の認証失敗 / コードのエラー | 報告で Omi にログ確認を依頼（`tail -40 tools/seedpipeline/out/logs/*.log`）。コード側の原因が分かれば修正して push |
| 抽出で同じエラーが繰り返される | Gemini の出力形式の変化、モデルの提供終了 | `seedpipeline/gemini.py` を修正。モデル変更は `config.py` の既定値 |
| 要確認（suspect）が多い | 地名の誤認、想定距離との照合が厳しすぎる | `seedpipeline/geo.py` の `build_geometry`。閾値は慎重に。地名の質は `gemini.py` のプロンプトで改善 |
| 移動区間のゴミが多い | 抽出プロンプトの規則が弱い | `gemini.py` の SYSTEM に除外規則を足す。出力側は `export.py` の `min_scenery` |
| 同じ道が複数に分かれる | 統合の閾値 | `seedpipeline/merge.py`。80% 重なりの閾値を下げる場合は慎重に |
| YouTube の枠切れで発見が進まない | 検索が多い | `config.py` の `search_pages_per_keyword` や `youtube_daily_budget` を調整 |

修正の作法:

- 変更は最小限にし、`cd tools/seedpipeline && python3 20260904_seed_pipeline.py selftest` を通してから push する
- コミットメッセージは日本語で「何を直したか」を書く
- 大きな設計変更や費用に影響する変更（API の呼び出し数が増えるもの）は、自分で push せず報告で提案し、Omi の判断を仰ぐ
- API キーはリポジトリに存在しない。キーが必要な検証は Omi に依頼する

## 3. 報告の書き方

- 宛先は Omi（鈴木 大海）。ですます調。技術用語はビジネスの言葉に置き換える
- 構成: ①今日の結果（実行の有無、増えた本数、累計）②品質所見（良い例・悪い例を数本）③今日直したこと（あれば。翌朝に自動反映される旨を添える）④Omi に依頼したいこと（無ければ「特になし」）⑤費用の注意（地図 API の呼び出し数が急増していれば言及）
- 数値は表か箇条書きで。長くしない（200〜400 字程度）
- 実行が無かった日は、その事実と考えられる原因、Omi に確認してほしいコマンドを 1 つだけ示す
