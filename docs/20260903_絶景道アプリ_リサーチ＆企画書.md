# 絶景道（Zekkei-do）アプリ リサーチ＆企画書

作成日: 2026-09-03
状態: 初版（Go/No-Go 判断用）
対象: iPhone（iOS 17 以降）を第一ターゲットとするバイクツーリング向けアプリ

---

## 0. 結論（要旨）

- 判断: **Go（開発推奨）**。ただし「ナビアプリ」ではなく「道の口コミプラットフォーム」として位置付けることが前提。
- 理由1: 日本国内には「道を区間単位で、ライダー自身が多軸評価し、それが蓄積される」アプリが確認できない。既存はナビ（ツーリングサポーター）、編集部キュレーション（ツーリングマップル Route!）、写真SNS（モトクル）の3類型。
- 理由2: 海外勢（calimoto / Scenic / Kurviger / REVER）は「ルート全体」への評価か、専門家が手作業で格付けした有料レイヤー（Butler Maps）であり、区間単位の投稿型評価は主戦場になっていない。日本の道路データも弱い。
- 理由3: 技術的な実現性は高い。GPS記録、区間の切り出し、地図表示、Google/Appleログイン、課金は、いずれも標準部品と低コストのクラウドサービスで構築可能。初期の固定費は月額数千円規模。
- 最大のリスクは技術ではなく「初期コンテンツ（絶景道データ）の空白」と「Apple審査での課金設計の扱い」。前者はYouTube動画を元にした手動シード投入、後者は「無料枠を残した上で投稿を特典扱いにする」設計で対応する。

## 1. 背景と課題認識

- バイクツーリングで欲しい情報は「目的地」ではなく「その道を走ること自体が気持ち良いか」。
- 既存アプリはナビ（最短・最適経路）とGPSログ（走った記録）が中心で、「この道は走ると景色が良い」という道単位の評価情報は、書籍・編集部記事・YouTube動画・SNSに散在している。
- 有名峠・ビーナスライン級は網羅されているが、「知られていないが、のどかで景色の良い道」は誰も体系的に集めていない。YouTubeのツーリング動画にはこうした道が多数登場する。

### 2.3 ポジショニングの整理

- 既存の「道の評価」は、(a) 専門家・編集部の手作業（Butler Maps、ツーリングマップル）か、(b) ルート全体へのいいね（calimoto、Scenic）の2種類。
- 本企画は「区間単位」「ライダーの多軸評価」「投稿で集積」という第3の型。自転車のStravaにおける「セグメント」機能の発想を、バイクの景観評価に転用するもの。
- ナビ機能は作らない（既存ナビに勝てず、開発コストも大きい）。ナビは「Googleマップ／ツーリングサポーターへルートを渡す」連携で済ませる。

## 3. プロダクト構想

### 3.1 コンセプト

「絶景道（ぜっけいどう）」= ライダーが「ここからここまで」と定義した、走って気持ちの良い道の区間。アプリはその発見・投稿・評価・閲覧に特化する。

### 3.2 主要機能（MVP）

1. **走行記録（GPSロガー）**: 発車から降車まで自動で走行軌跡を記録。バックグラウンドでも記録を継続。
2. **絶景道の切り出し**: 記録した軌跡の中から、地図上のスライダーで「開始点」「終了点」を指定し、その区間だけを絶景道として登録。自宅周辺は既定で除外される（プライバシーゾーン）。
3. **多軸評価**: 以下を5段階で入力。
   - 絶景度
   - 走りやすさ（路面の良さ・道幅）
   - ワインディング度
   - 休憩所の有無（道の駅・売店・トイレ）
   - 絶景スポットでの駐車可否
   - 任意: 交通量、おすすめの季節・時間帯、コメント
   - **写真・動画の添付**: 写真は最大5枚（端末側で縮小）、短い動画は1本（30秒・720pに自動圧縮）。長い動画はYouTube等のURLで紹介する。配信コストを抑えつつ「道の雰囲気」を伝える設計
4. **絶景道の閲覧**: 地図上で周辺の絶景道を色分け表示。詳細画面で評価の平均、投稿数、コメント、写真、YouTube動画リンクを表示。
5. **ログイン**: Googleログイン＋Appleでサインイン（後者はApple審査上の必須要件、5.2参照）。
6. **通報・ブロック・フィルタ**: 投稿型アプリとしてApple審査上の必須要件。
7. **ルートの引き渡し**: 絶景道の始点・終点をGoogleマップ等に渡してナビさせる。

### 3.3 データ設計の要点（「同じ道」の扱い）

- ユーザーが切り出した区間が、既存の絶景道と大部分（例: 70%以上）重なる場合は、新規作成ではなく既存の絶景道への「評価追加」として扱う。これにより同じ道が乱立せず、評価が集積される。
- 重なり判定は、道路に沿って補正した軌跡同士の重なり長で行う。専門的には「マップマッチング」と「空間検索」と呼ばれる処理で、いずれも既製サービスで対応可能。

### 3.4 初期コンテンツ戦略（ゼロからの立ち上げ）

- 公開時点で地図が空では使われない。YouTubeのツーリング動画から道を特定し、運営側で「シード絶景道」を100〜300本投入する。
- YouTube動画は、動画そのものをアプリ内で再生するのではなく「リンク＋サムネイル」として紐付ける（YouTubeの規約上、埋め込み再生を課金で制限することは不可のため、動画は無料側に置く）。
- 動画投稿者への還元（チャンネルリンクの明示）を設計に含め、投稿者コミュニティとの協業余地を残す。
- Omiから提供予定のサンプル動画は、この「シード投入」の最初の対象とする。

## 4. 課金設計案

### 4.1 基本方針

- 収益源は「絶景道の閲覧枠」。投稿・記録は常に無料。
- ユーザーは以下のいずれかを自分で選ぶ。
  - **投稿コース**: 月あたり数件の無料閲覧枠に加え、絶景道を1件投稿するごとに閲覧枠を付与（例: 投稿1件につき3件）。
  - **サブスクコース**: 月額数百円で閲覧無制限。

### 4.2 Apple審査上の留意点（重要）

- Apple審査ガイドライン 3.2.2 (vi) は、「動画視聴や他アプリのダウンロード等の行動を機能・コンテンツ利用の条件にすること」を禁じる。投稿を閲覧の唯一の条件にすると、この条項に抵触するとみなされるリスクがある。
- 対応: 無料の閲覧枠を常に用意し、投稿による枠付与は「特典」として設計する。閲覧無制限はサブスク（アプリ内課金）でも到達できる状態にする。Glassdoorの「Give to Get」方式に近い運用だが、無料枠と課金導線を両方残す点で審査耐性を高める。
- 3.1.1: 課金で購入した閲覧枠は失効させてはならない（購入枠は無期限、投稿で得た特典枠のみ月次リセットという分離が必要）。
- 課金の実装はAppleの標準仕組み（アプリ内課金）を使い、管理はRevenueCat等の課金管理サービスに任せる（月間売上$2,500まで無料）。

### 4.3 価格の目安

- サブスク: 月額 300〜480円。競合（ツーリングサポーター月額数百円、Route! 月額600円）より下に置き、「ナビの追加」として同居できる価格にする。
- 年額: 月額の10か月分相当。

## 5. 技術構成（ビジネス用語での説明）

### 5.1 全体像

| 役割 | 採用候補 | 業務上の意味 | 費用 |
|---|---|---|---|
| アプリ本体 | Swift / SwiftUI（Apple標準） | iPhoneアプリの「店舗」 | 無料（Mac＋Xcodeが必要） |
| 地図表示 | Apple MapKit（標準） | 地図の「什器」。Apple標準は無料で、審査も通りやすい | 無料 |
| 走行記録 | Core Location（標準） | 「足跡」を記録する仕組み。バックグラウンド記録可 | 無料 |
| 会員・DB・写真/動画保管 | Supabase（PostGIS付き） | 会員台帳と「地図が読める台帳」。区間の重なり判定が得意。写真・動画の倉庫も兼ねる | 無料枠あり、本番 $25/月〜。動画は配信量課金のため30秒・720pに圧縮して抑制 |
| 道路への補正 | Mapbox Map Matching API | ぶれたGPS点を道路上に貼り付ける補正 | 月10万リクエストまで無料 |
| ログイン | Google + Appleでサインイン | 会員登録の受付 | 無料 |
| 課金 | StoreKit 2 + RevenueCat | Appleのレジと、その売上台帳 | 売上$2,500/月まで無料 |
| 配布 | Apple Developer Program | 出店契約 | 年額 $99（約13,000〜15,000円） |

### 5.2 Apple審査で押さえるべき要件

1. 1.2 投稿コンテンツ: 不適切投稿のフィルタ、通報機能と24時間以内の対応、ユーザーのブロック、連絡先の公開。
2. 4.8 ログイン: Googleログインを提供する場合、名前とメールのみ・メール非公開が可能・広告目的で行動収集しない、というログインを併設する必要がある。実務上は「Appleでサインイン」を追加すれば充足。
3. 5.1.5 位置情報: 取得前に目的を説明し同意を得る。バックグラウンド記録には「常に許可」が必要で、審査で用途説明を求められる。
4. 3.1.1 課金: コンテンツ解放はアプリ内課金のみ。外部決済への誘導は不可。

### 5.3 端末バッテリーへの配慮

- 走行中は高精度で記録し、停車が続けば自動で記録を一時停止する。
- ツーリング1回（6〜8時間）でバッテリーを使い切らないよう、精度・記録間隔を可変にする。バイク側のUSB給電が前提の利用者が多い点も踏まえ、初期は「記録中は給電推奨」と明示する。

### 5.4 開発体制上の前提

- iPhoneアプリの実行・審査提出にはmacOS＋Xcodeが必須。本リポジトリのコードはLinux環境で作成しており、コンパイル確認は未実施。Mac上でのビルド確認が次の作業となる。

## 8. 確認事項・未確定事項（Omiへの相談）

1. YouTubeサンプル動画: 17本を受領済み。12本をシード投入、5本は視聴による区間特定が必要（`docs/20260904_YouTubeシード動画リスト.md`）。
2. アプリ名: 仮称「絶景道（Zekkei-do）」。商標・App Store上の重複確認が必要。
3. 対象地域: 初期は関東・甲信越に絞るか、全国か。シード投入の工数に直結する。
4. 課金コースの初期値: 無料閲覧枠（月3件案）、投稿1件あたりの付与枠（3件案）、月額（380円案）。
5. Mac環境: Mac mini（常時起動）で確保済み。
6. Apple Developer Program: 法人（TidalWorks、登記予定 2026年10月上旬）で登録する方針。登記後に D-U-N-S 番号を申請し、その後 Apple に申請。会社ドメインのメールで申請する。TestFlight 配布はこの完了後。
