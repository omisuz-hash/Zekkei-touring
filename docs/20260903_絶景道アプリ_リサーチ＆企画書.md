# 絶景道（Zekkei-do）アプリ リサーチ＆企画書

作成日: 2026-09-03
状態: 初版（Go/No-Go 判断用）
対象: iPhone（iOS 17 以降）を第一ターゲットとするバイクツーリング向けアプリ

---

## 0. 結論（要旨）

- 判断: **Go（開発推奨）**。ただし「ナビアプリ」ではなく「道の口コミプラットフォーム」として位置付けることが前提。
- 理由1: 日本国内には「道を区間単位で、ライダー自身が多軸評価し、それが蓄積される」アプリが確認できない。既存はナビ（ツーリングサポーター）、編集部キュレーション（ツーリングマップル Route!）、写真SNS（モトクル）の3類型。
- 理由2: 海外勢（calimoto / Scenic / Kurviger / REVER）は「ルート全体」への評価か、専門家が手作業で格付けした有料レイヤー（Butler Maps）であり、区間単位の投稿型評価は主戦場になっていない。日本の道路データも弱い。
- 理由3: 技術的な実現性は高い。GPS記録、区間の切り出し、地図表示、Google/Appleログイン、課金は、いずれも標準部品と低コストのクラウドサービスで構築可能。初期の固定費は月額数千円規模。
- 最大のリスクは技術ではなく「初期コンテンツ（絶景道データ）の空白」と「Apple審査での課金設計の扱い」。前者はYouTube動画を元にした手動シード投入、後者は「無料枠を残した上で投稿を特典扱いにする」設計で対応する。

## 1. 背景と課題認識

- バイクツーリングで欲しい情報は「目的地」ではなく「その道を走ること自体が気持ち良いか」。
- 既存アプリはナビ（最短・最適経路）とGPSログ（走った記録）が中心で、「この道は走ると景色が良い」という道単位の評価情報は、書籍・編集部記事・YouTube動画・SNSに散在している。
- 有名峠・ビーナスライン級は網羅されているが、「知られていないが、のどかで景色の良い道」は誰も体系的に集めていない。YouTubeのツーリング動画にはこうした道が多数登場する。

### 2.3 ポジショニングの整理

- 既存の「道の評価」は、(a) 専門家・編集部の手作業（Butler Maps、ツーリングマップル）か、(b) ルート全体へのいいね（calimoto、Scenic）の2種類。
- 本企画は「区間単位」「ライダーの多軸評価」「投稿で集積」という第3の型。自転車のStravaにおける「セグメント」機能の発想を、バイクの景観評価に転用するもの。
- ナビ機能は作らない（既存ナビに勝てず、開発コストも大きい）。ナビは「Googleマップ／ツーリングサポーターへルートを渡す」連携で済ませる。

## 3. プロダクト構想

### 3.1 コンセプト

「絶景道（ぜっけいどう）」= ライダーが「ここからここまで」と定義した、走って気持ちの良い道の区間。アプリはその発見・投稿・評価・閲覧に特化する。

### 3.2 主要機能（MVP）

1. **走行記録（GPSロガー）**: 発車から降車まで自動で走行軌跡を記録。バックグラウンドでも記録を継続。
2. **絶景道の切り出し**: 記録した軌跡の中から、地図上のスライダーで「開始点」「終了点」を指定し、その区間だけを絶景道として登録。自宅周辺は既定で除外される（プライバシーゾーン）。
3. **多軸評価**: 以下を5段階で入力。
   - 絶景度
   - 走りやすさ（路面の良さ・道幅）
   - ワインディング度
   - 休憩所の有無（道の駅・売店・トイレ）
   - 絶景スポットでの駐車可否
   - 任意: 交通量、おすすめの季節・時間帯、コメント
   - **写真・動画の添付**: 写真は最大5枚（端末側で縮小）、短い動画は1本（30秒・720pに自動圧縮）。長い動画はYouTube等のURLで紹介する。配信コストを抑えつつ「道の雰囲気」を伝える設計
4. **絶景道の閲覧**: 地図上で周辺の絶景道を色分け表示。詳細画面で評価の平均、投稿数、コメント、写真、YouTube動画リンクを表示。
5. **ログイン**: Googleログイン＋Appleでサインイン（後者はApple審査上の必須要件、5.2参照）。
6. **通報・ブロック・フィルタ**: 投稿型アプリとしてApple審査上の必須要件。
7. **ルートの引き渡し**: 絶景道の始点・終点をGoogleマップ等に渡してナビさせる。

### 3.3 データ設計の要点（「同じ道」の扱い）

- ユーザーが切り出した区間が、既存の絶景道と大部分（例: 70%以上）重なる場合は、新規作成ではなく既存の絶景道への「評価追加」として扱う。これにより同じ道が乱立せず、評価が集積される。
- 重なり判定は、道路に沿って補正した軌跡同士の重なり長で行う。専門的には「マップマッチング」と「空間検索」と呼ばれる処理で、いずれも既製サービスで対応可能。

### 3.4 初期コンテンツ戦略（ゼロからの立ち上げ）

- 公開時点で地図が空では使われない。YouTubeのツーリング動画から道を特定し、運営側で「シード絶景道」を100〜300本投入する。
- YouTube動画は、動画そのものをアプリ内で再生するのではなく「リンク＋サムネイル」として紐付ける（YouTubeの規約上、埋め込み再生を課金で制限することは不可のため、動画は無料側に置く）。
- 動画投稿者への還元（チャンネルリンクの明示）を設計に含め、投稿者コミュニティとの協業余地を残す。
- Omiから提供予定のサンプル動画は、この「シード投入」の最初の対象とする。

### 3.x 匿名性と投稿のハードル（2026-09-07 追記）

- **ログインは必須、表示は匿名**。荒らし・なりすましの抑止のためログイン（Apple / Google）は求めるが、公開されるのはユーザーが決めたニックネームのみ。実名・アイコン・メールアドレスは取り込まず、登録時は「ライダー0142」のような仮名を自動で割り当てる。ニックネームは 2〜20 文字、URL やアカウント名は不可、変更は随時可能。
- 匿名運用でも通報・ブロックの対象は内部の利用者IDで追えるため、悪質な投稿への対処は成立する。
- **写真・動画は走行記録の有無を問わず投稿できる**。GPSで記録した区間からの投稿に加え、道の詳細画面からいつでも追加できる。過去のツーリングで撮った写真を後日あげたい需要に応え、初期の写真不足を利用者側から埋める狙い。

### 3.y データベースの安全設定（2026-09-09 追記）

Supabase の Security Advisor の指摘に対する方針。

- **対処済み**: 更新履歴の表（`schema_migrations`）に行レベル保護を追加。全関数の参照先スキーマを `public` に固定。関数の実行権限を、アプリが実際に呼ぶ 5 つ（周辺の道の取得・区間の重なり判定・閲覧枠の残数・道の閲覧・ニックネーム変更）に限定。
- **受容（対処不要）**: `spatial_ref_sys`（座標系の定義表）、`postgis` が公開スキーマにある件、PostGIS 自身の関数 3 件。いずれも地図機能の付属品で、利用者データを含まず、こちらから設定を変更できない。
- **対処済み（2026-10-09）**: 匿名ログイン（ゲスト）からの書き込みを停止。投稿・評価・写真・通報・走行記録は正規のログイン（Apple / Google）が必要。閲覧は匿名のまま。
- **対処済み（2026-10-09）**: アプリ内からのアカウント削除（Apple ガイドライン 5.1.1(v)）。本人の情報は削除し、公開済みの絶景道は残して投稿者との結び付けのみ外す。
### 3.b 地域（Region）と初期表示（2026-10-07 追記）

全国を扱うが、利用者が毎回全国を見るわけではない。関東在住者が関西の道を初期表示で見たい場面は想定しにくい。そこで「よく走る地域」を端末に保存し、起動時はその地域から見せる。

- 地域は 10 区分（北海道・東北・関東・甲信越・北陸・東海・関西・中国・四国・九州沖縄）。都道府県で定義し、地図上の中心と広さを持つ。
- 初回起動時に地域の選択を促す。現在地の権限がある場合は一番近い地域を初期値にする。マイページと地図上のボタンからいつでも変更可能。
- **起動直後はその地域の代表的な 30 本のみ**を表示する。初見での見やすさを優先する。地図を動かした時点で従来の縮尺連動の表示本数に戻る。
- 地域はあくまで初期表示用。境界で表示が切れることはなく、地図を動かせば地域をまたいでシームレスに見られる仕様は変えない。
- 保存先は端末内（ログイン不要）。将来、複数端末で揃える必要が出た段階でプロフィールへの保存を検討する。

### 3.c ビジュアル調達の方針（2026-10-07 追記）

**Instagram からの取得は現実的でないと判断**。理由は 4 点。
1. ハッシュタグ検索は Instagram Graph API に存在するが、利用には Business/Creator アカウント、Facebook アプリ、公開コンテンツ閲覧権限の審査が要る。この権限の付与は厳しく絞られている。
2. 件数制限が 7 日間で 30 ハッシュタグ程度。対象が 2,000 本超の規模には全く足りない。
3. 規約上、取得した画像の保存・キャッシュが認められていない。URL も期限切れになる。アプリ側で代表画像として持つ運用と噛み合わない。
4. 投稿者それぞれに著作権がある。API の制約とは別に、商用アプリでの再掲は権利処理が要る。

**採る方針は 4 本立て。**
- 短期: 代表動画のサムネイルを地図のタグに出す（実装済み）。公式のサムネイル URL の利用であり、動画へのリンクと併記する限り問題ない。
- 中期: 同じ動画から複数ある自動生成サムネイル（0〜3）のうち、最も絶景らしい 1 枚を Gemini に選ばせる。追加の権利処理不要、費用は 1 本あたり 1 円未満。
- 継続: Wikimedia Commons・Wikipedia の自由ライセンス写真（運用中）。
- 本命: 利用者による写真投稿。走行記録の有無を問わず投稿できる導線は実装済み。評価と併せて投稿を促す設計を今後詰める。

### 3.d 他アプリからの走行記録の取り込み（2026-10-07 追記）

既にナビや記録アプリを使っている人に、絶景道を二重に立ち上げさせるのは現実的でない。他アプリの書き出しを取り込める方が、投稿の敷居が大きく下がる。

GPX が事実上の共通形式であり、ツーリング・サイクリング・登山系の主要アプリはほぼ対応している（ツーリングサポーター、Strava、Garmin Connect、Ride with GPS、ヤマレコ、YAMAP など）。KML は Google マップ系、TCX は Garmin 系で使われる。

実装: GPX / KML / TCX の 3 形式に対応。入口は 2 つ。
1. 「走行記録」タブの「他のアプリの記録を取り込む」から、ファイルアプリ経由で選ぶ（複数まとめて可）。
2. 他アプリの共有メニューから「絶景道」を選ぶ。

取り込んだ記録は自分で記録したものと同じ扱いになり、区間の切り出しから投稿までそのまま進める。記録は端末内にのみ保存され、公開するのは切り出した区間だけという方針も変わらない。

プライバシーの扱い: 他アプリの記録は自宅の出発・到着を含むことが多い。プライバシーゾーン（自宅周辺を切り出し時に自動除外する設定）が未設定の場合、「走行記録」タブに常時の案内を出し、取り込み直後にも設定を促す。設定画面は共用の部品にして、マイページ・案内・取り込み後のどこからでも同じものを開く。

### 3.z 無料枠の自動停止対策（2026-09-17 追記）

Supabase の無料枠は、7 日間「利用実績」が無いとプロジェクトが自動停止される（停止後 90 日以内なら再開可能）。注意すべき点は、**毎晩の流し込みは管理 API（Personal Access Token）経由のため、この利用実績に数えられない**こと。アプリをシミュレーターで開かない日が続くと、実際には稼働していても無通信と判定される。

対策として、毎晩の自動実行の最後に、アプリと同じ経路（REST API + アプリ用の鍵）で 1 回読む処理（`db_admin.py ping`）を追加した。費用はかからない。

**2026-09-25 更新**: 対策を入れた後も 9/18 に一度自動停止され、9/24 に再び停止予告が届いた。1 日 1 回の疎通では「十分な利用」と判定されない模様。停止中は毎晩の流し込みが失敗し、収集結果が手元に溜まるだけになる（収集自体は継続）。TestFlight を待たず、**Pro プラン（月 25 ドル）への移行を推奨**する。自動停止の解消に加えて日次バックアップが付き、毎朝の自動処理が止まらなくなる。

（参考）Pro に移行しない場合の代替は、疎通確認を 1 日 4〜6 回に増やす運用。ただし Supabase の判定基準は公開されていないため、確実性は無い。

### 3.aa Data API の権限（2026-10-30 の仕様変更）

2026-10-30 以降、`public` スキーマに新しく作る表は、明示的に権限を与えないとアプリから見えなくなる。既存の表は影響を受けない。**今後の変更で表を追加する際は、作成と同じファイル内で権限も与えること**（`20260924_data_api_grants.sql` が参考例）。プロジェクトを作り直す場合に備え、既存の全表の権限も同ファイルで明示済み。

- `rls_auto_enable()` は Supabase が標準で持つ安全装置。公開スキーマに表を作ると自動で保護を有効にする仕組みで、こちらで作成したものではない。

## 4. 課金設計案

### 4.1 基本方針

- 収益源は「絶景道の閲覧枠」。投稿・記録は常に無料。
- ユーザーは以下のいずれかを自分で選ぶ。
  - **投稿コース**: 月あたり数件の無料閲覧枠に加え、絶景道を1件投稿するごとに閲覧枠を付与（例: 投稿1件につき3件）。
  - **サブスクコース**: 月額数百円で閲覧無制限。

### 4.2 Apple審査上の留意点（重要）

- Apple審査ガイドライン 3.2.2 (vi) は、「動画視聴や他アプリのダウンロード等の行動を機能・コンテンツ利用の条件にすること」を禁じる。投稿を閲覧の唯一の条件にすると、この条項に抵触するとみなされるリスクがある。
- 対応: 無料の閲覧枠を常に用意し、投稿による枠付与は「特典」として設計する。閲覧無制限はサブスク（アプリ内課金）でも到達できる状態にする。Glassdoorの「Give to Get」方式に近い運用だが、無料枠と課金導線を両方残す点で審査耐性を高める。
- 3.1.1: 課金で購入した閲覧枠は失効させてはならない（購入枠は無期限、投稿で得た特典枠のみ月次リセットという分離が必要）。
- 課金の実装はAppleの標準仕組み（アプリ内課金）を使い、管理はRevenueCat等の課金管理サービスに任せる（月間売上$2,500まで無料）。

### 4.3 価格の目安

- サブスク: 月額 300〜480円。競合（ツーリングサポーター月額数百円、Route! 月額600円）より下に置き、「ナビの追加」として同居できる価格にする。
- 年額: 月額の10か月分相当。

## 5. 技術構成（ビジネス用語での説明）

### 5.1 全体像

| 役割 | 採用候補 | 業務上の意味 | 費用 |
|---|---|---|---|
| アプリ本体 | Swift / SwiftUI（Apple標準） | iPhoneアプリの「店舗」 | 無料（Mac＋Xcodeが必要） |
| 地図表示 | Apple MapKit（標準） | 地図の「什器」。Apple標準は無料で、審査も通りやすい | 無料 |
| 走行記録 | Core Location（標準） | 「足跡」を記録する仕組み。バックグラウンド記録可 | 無料 |
| 会員・DB・写真/動画保管 | Supabase（PostGIS付き） | 会員台帳と「地図が読める台帳」。区間の重なり判定が得意。写真・動画の倉庫も兼ねる | 無料枠あり、本番 $25/月〜。動画は配信量課金のため30秒・720pに圧縮して抑制 |
| 道路への補正 | Mapbox Map Matching API | ぶれたGPS点を道路上に貼り付ける補正 | 月10万リクエストまで無料 |
| ログイン | Google + Appleでサインイン | 会員登録の受付 | 無料 |
| 課金 | StoreKit 2 + RevenueCat | Appleのレジと、その売上台帳 | 売上$2,500/月まで無料 |

### 5.2 Apple審査で押さえるべき要件

## 10. 有料化の段階（2026-11-22 時点の想定）

公開版は無料・課金なしで出す。ここでは、その後どう回収に向かうかを置いておく。

### 10.1 いまの持ち出し（概算）

| 項目 | 月あたり |
|---|---|
| Supabase Pro（$25） | 約 4,000 円 |
| Apple Developer Program（年 15,000 円） | 約 1,250 円 |
| ドメイン・メール | 約 400 円 |
| 地図 API・Gemini（従量） | 収集の稼働次第 |
| **固定費の合計** | **約 5,500〜6,000 円** |

年間でおよそ 7 万円。これが当面の回収目標になる。
利用者が増えると保管と転送の費用も乗るため、固定ではない点に注意する。

### 10.2 課金に進む判断基準

**次の 3 つが揃うまでは入れない。**

1. 自分以外の投稿者が、月に数人いる
2. **閲覧枠を使い切る人が一定割合いる**
3. 一度入れた人が、翌月も開いている

**2 がいちばん重要になる。**枠が余っている状態で課金を置いても誰も買わない。
枠が足りないという声が出て初めて、有料の選択肢に意味が生まれる。

### 10.3 段階

**第 1 段: 閲覧枠の追加購入（消耗型）**

最初の課金はこれを推奨する。理由は実装と審査がいちばん軽いこと。
消耗型は、解約の導線・購入の復元・家族共有といった定期購読の要件がかからない。

**受け皿は既にある。**閲覧枠の台帳には `purchased` という種別があり、
失効しない枠として扱われる。解放時も失効しない枠から先に使う作りになっている。
アプリ側に購入の画面を足せば繋がる。

買わなくても毎月の無料枠は残るため、「投稿しないと見られない」設計にはならない
（ガイドライン 3.2.2 (vi) への対応を維持できる）。

**第 2 段: 閲覧無制限の買い切り**

消耗型で需要が確かめられてから。

**ツーリングは季節性が強い。**冬に解約される定期購読より、買い切りの方が合う。
使う人にとっても分かりやすい。

### 10.3.1 価格（2026-11-22 修正）

Apple の価格設定は、日本円で 50 円から 160 万円まで 900 段階。2,000 円までは
細かい刻みで選べるため、金額の制約は実質無い。

**比較対象は Route!（ツーリングマップル）の全エリア 600 円。**昭文社が長年の取材
データを開放している価格であり、無名のアプリがこれを超える値付けをするのは筋が通らない。
当初案の 1,200〜1,800 円は高すぎる。

| 商品 | 価格 | 位置づけ |
|---|---|---|
| 閲覧枠 20 個 | 200 円 | 今月あと少し足りない人向け |
| **閲覧無制限（買い切り）** | **600 円** | 本命 |

3 つ以上並べると選択に迷いが出るため、2 つに絞る。
枠 20 個が 1 枠 10 円に対し、無制限は 60 個分の値段で無期限となるため、
ある程度使う人には無制限が得だと一目で分かる。

**商品名は「閲覧無制限」とし、「Pro」「全機能」にはしない。**将来コース作成などの
新機能を作ったとき、「全機能」で売っていると購入者全員に無償で含めることになる。
名前を閲覧に限定しておけば、新機能を別建てにする余地が残る。後から狭めることは
できないため、最初から範囲を絞る。

**第 3 段: 定期購読、または送客（規模が出てから）**

定期購読は継続 20 人で固定費を賄えるが、解約の波を受ける。
立ち寄りスポットから宿や飲食店への送客は筋がよいが、相応の利用者数が要る。

### 10.4 やらない方がよいもの

- **広告**: 体験を損なううえ、投稿が少ないうちは単価も出ない
- **早すぎる定期購読**: 実装も審査も重く、価値が育つ前だと解約率が高い
- **公開と同時の課金**: 競合が全て無料ダウンロードのため、価格表示だけで候補から外れる

### 10.5 損益分岐（概算）

Apple の手数料は小規模事業者向けの 15% とする（手取り 85%）。
固定費を月 6,000 円としたとき、

| 形 | 手取り | 必要な数 |
|---|---|---|
| 閲覧無制限 600 円 | 510 円 | **月 12 件** |
| 枠 20 個 200 円 | 170 円 | 月 35 件 |
| 定期購読 380 円 | 323 円 | 継続 19 人 |

**月 12 件の買い切りで固定費が出る。**利用者が数百人いれば届く水準である。

### 10.6 急がない理由

年 7 万円は、投稿が育つまでの投資として見る方が合理的である。
早く課金すると母数が減り、投稿も減り、価値そのものが育たない。
口コミの地図は、集まった投稿の量がそのまま商品になるため、
最初に削ってはいけないのが利用者数になる。

### 11.1 しょうたろうモトブログ様（動画投稿者、iPhone）

シード貢献のお礼として招待コードを送付した方からの返信。インストールと
コード適用を完了したうえでの感想。初めて得た、開発関係者以外からの

**評価された点**

- 「探す」が最初に来る構成のため、何をするアプリかは伝わる
- 日本地図全体から拡大して探す流れ。「箱根方面に行くが良い道はないか」から
  「こんな道があるのか」への発見が成立
- 有名な道でも知らない区間が多いという気づき
- **Google マップへのルート受け渡しが最高評価**（原文「めちゃくちゃ良い」「使ってみたいと思った」）。
  現在地からの出発も評価
- ツーリングの計画時はブログや YouTube で探すことが多く、本アプリで探せるのは便利
- YAMAP のバイク版を思わせる作り

**指摘された課題**

1. **道の情報が多すぎる感がある。** ライトユーザー向けか玄人向けかが不明瞭。
   ライトユーザーからは、どの道が定番なのか判別しづらい
2. **候補に出る紹介動画に、観覧性の低いものが混在している**
3. **記録して投稿する用途が想像しづらい**（ただし作りとしては面白いとの評価）

### 11.2 分析

**ポジショニングの課題は、インストール前に限定される。**
知人から出ていた「ナビなのか」「併用できるのか」という疑問は、本件では
発生していない。アプリを開けば伝わるという裏付けであり、課題は紹介ページ
および App Store の掲載情報の側にある、と切り分け可能。

**「定番が分からない」の根本原因は、定番度が画面に出ていないこと。**
現状、地図上の強調度（`tagLevel`）は絶景度のみで決まる（4.5 以上／3.5 以上）。
動画での言及数（`mentionCount`）は `prominence` に含まれるが、その用途は
重なったときの描画順序のみ。絶景度は動画からの推定値であるため、
マイナーな道でも高く出る。結果として、定番の道と無名の道が同じ重みで並ぶ。

**投稿が想像しづらいのは構造的。**
新規の道の投稿には走行記録が必須であり、「探す」から「投稿する」までの
距離が遠い。探すために入った利用者が、その日のうちに投稿へ到達する経路がない。

**最大の価値は Google マップへの受け渡しにある。**
評価が最も高かった機能が、月ごとの閲覧枠の内側にある。課金設計としては
正しい配置だが、価値を体験する前に壁が来る構造である点は留意を要する。

### 11.3 対応案

| 優先 | 施策 | 内容 | 状況 |
|---|---|---|---|
| 高 | 定番度の可視化 | 紹介数を地図の配色に反映 | **対応済み（2026-11-25）。11.5 を参照** |
| 中 | 絞り込み | 「定番の道だけ」「評価の高い順」での表示切り替え | 未着手 |
| 中 | 紹介動画の品質 | シード収集時に再生回数・評価率での下限を設定。既存データの見直し | 未着手 |
| **高** | 投稿への導線 | 地図から区間を指定して投稿する経路の追加 | **未着手。優先度を引き上げ（2026-11-25）。11.6 を参照** |

### 11.4 保留とする判断

「定番度の可視化」以外は即時着手しない。n=1 であり、同じ指摘が複数から
出るかを待つ。

### 11.5 定番度の可視化（2026-11-25 対応済み）

地図の配色を「絶景度」と「定番度」で切り替えられるようにした。

**背景**

紹介数（動画での言及数 + 投稿数）はデータとして持っていたが、重なった
ときの描画順序にしか効いておらず、画面には出ていなかった。地図上の
強調度は絶景度のみで決まっていた。絶景度は動画からの推定値であるため、
マイナーな道でも高く出る。結果として、定番の道と無名の道が同じ重みで
並んでいた。

**実装**

| 尺度 | 配色 | 段階 |
|---|---|---|
| 絶景度 | ブルー | 4.5 以上 / 3.5 以上 / グレー |
| 定番度 | アンバー | 紹介 10 件以上 / 3 件以上 / グレー |

しきい値はシードの分布から決定。11/25 時点で言及のある道は 4,669 本、
うち 1 件のみが 61%、10 件以上が 359 本（約 8%）、3 件以上が 1,183 本（約 25%）。

**クロス表示**

もう一方の尺度でも最上段の道には、その尺度の色を細く重ねる。定番度
（オレンジ）の上にブルーが乗れば「絶景度も高い」と読める。当初は白線で
表していたが、どちらの軸の話か読み取れないとの指摘を受けて変更した。

**併せて修正した構造的な問題**

`nearby_roads` が件数上限をかける順序は絶景度寄りに固定されていた。
そのため、定番度で色を塗っても紹介数の多い道が画面に出てこない場合が
あった。`p_order` を追加し、尺度に合わせて拾う順序を変えられるようにした。

**UI の整理**

地図右下の操作を縦一列（拡大縮小 / 地図の種類 / 現在地）に整理。尺度の
切り替えはアイコンでは意味が伝わらないため、左下の凡例の最下行に
「◯◯に切り替える」という文言で配置した。コンパスは常に北を指すだけで
情報がないため削除した。

### 11.6 走行記録の消失と、投稿導線の優先度引き上げ（2026-11-25）

**発生した事象**

アプリを削除して入れ直したところ、端末内の走行記録が失われた。走行記録は
自宅周辺を含むためサーバーへ送らない設計であり、仕様どおりの挙動である。
投稿済みの絶景道はサーバーにあるため無事。失われたのは軌跡のみ。

**影響範囲**

開発者固有の問題ではない。機種変更、アプリの入れ直し、端末の故障の
いずれでも同じことが起きる。しかも**記録を失うと、その道はもう投稿できない**。
新規投稿には走行記録が必須であるため。

**対応（同日実装）**

| 施策 | 内容 |
|---|---|
| まとめて書き出し | 走行記録の画面に「すべてまとめて書き出す」を追加。GPX で一括出力し、ファイルアプリや iCloud Drive に保存できる。読み込み側の仕組みは既存 |
| 注意書き | 同画面に「この端末にのみ保存されます。アプリを削除すると消えます」を常時表示 |
| 版の表示 | マイページ下部に「バージョン 1.0.1 (ビルド番号)」を表示。問い合わせ時の確認用 |

**投稿導線の優先度引き上げ**

「地図から区間を指定して投稿する経路」は、当初「要望が増えてから」と
整理していた。今回、**記録消失という別の理由が加わった**ため、優先度を
高に引き上げる。

この経路があれば以下が同時に解決する。

- 記録を失った道も投稿できる
- 探すために入った利用者が、その日のうちに投稿へ到達できる
  （しょうたろう様の「記録して投稿するのはイメージが沸かない」への対応）
- 他アプリで記録している利用者も投稿できる

**バックアップそのものは実装しない。** 走行記録をサーバーへ送らない方針は
プライバシー設計の中核であり、変更しない。利用者が自分で書き出せる手段を
用意するところまでを範囲とする。

### 11.7 ルート作成・共有への要求の一致（2026-11-27）

公開のご案内に対する返信のなかで、独立した複数の情報源が同じ方向を
指した。判断の分かれ目になる記録として残す。

**三つの情報源**

| 出どころ | 内容 |
|---|---|
| しょうたろう様（利用者） | 「記録して投稿するのはイメージが沸かない」。走行記録が必須という制約への指摘 |
| お燐様（利用者） | 「動画を投稿しているかどうかにかかわらず、誰でも自分のおすすめのツーリングルートを作って共有できたら面白そう」「地元のライダーが普段走っているお気に入りの道も知るきっかけになりそう」 |
| 開発者自身（2026-11 中旬） | 複数の絶景道を組み合わせたい。ナビはスコープ外とし、ルート探索・作成・記録・共有に特化する |

**読み取れること**

否定ではなく要求である。しょうたろう様は「投稿の入口が遠い」という形で、
お燐様は「作って共有したい」という形で、同じ欠落を指している。

走行記録が必須という制約が、二つの機会を同時に閉じている。地元の道を
よく知る人が共有できない。走らずに組み立てたいルートが作れない。

**併せて寄せられた提案（お燐様）**

ルートに対する「走ってみたい」投票と、そのポイントによるランキング。
投稿する側の張り合いと、行き先を探す側の手がかりを同時に満たす設計。
開発者が以前に構想した「投稿数の可視化によるランキング」とは軸が異なり、
投稿者ではなくルートを評価の対象とする。

**判断**

「コース作成についての意見が多く出てきたら検討する」という保留の条件は、
満たされたと考えてよい。11.3 の対応表で「地図から区間を指定して投稿する
経路」として挙げていた項目は、より広く「ルートの作成と共有」として
捉え直す必要がある。

ただし着手の順序は、他の候補（Android 版、ランキング、自分の記録のみ表示、
ライトモード、動画の品質基準、重複した道の整理）と並べて判断する。

### 11.8 全国表示のタイムアウトと、今後の監視点（2026-11-28）

**発生した事象**

利用者より、地図を全国まで引いた状態で「canceling statement due to
statement timeout」というエラーが表示されるとの報告。道を探す問い合わせが
データベース側の制限時間に収まらなかった。

**原因（実行計画で確認済み）**

三つが重なっていた。

1. 自動収集により道が増え続けていた（この時点で公開中 4,313 本）
2. 20261125 の対応で並べ替えの先頭に case 式を置き、索引が使えなくなっていた
3. 半径 1,200km の距離計算を全件に対して行っていたが、その範囲は実質的に
   日本全体であり、絞り込みの効果がなかった

3 については実行計画が明確に示していた。`Rows Removed by Filter: 16` ——
4,296 本のうち距離の条件で除外できたのは 16 本のみ。ほぼ全件に対して
地理距離の計算を行いながら、何も絞り込めていなかった。

**対応（20261128_nearby_roads_speed.sql）**

- 並べ替えを支える部分索引を追加（公開中の道のみを対象とする）
- `nearby_roads` を尺度ごとの分岐に書き換え、case 式を外した
- 半径が 1,000km 以上の場合は距離計算そのものを省く
- 英語のエラー文がそのまま利用者に出ていたため、日本語への言い換えを追加
  （`ZKError.humanized`）

**効果**

| 測定 | 所要時間 |
|---|---|
| 修正前と同じ形の問い合わせ | 569 ms |
| 修正後、アプリが呼ぶ関数 | 48 ms |

**今後の監視点**

全国表示は距離計算を省くため、本数が増えても影響を受けにくい。一方で
**中間の縮尺（地方単位の表示）は距離計算が走るため、本数にほぼ比例して
重くなる。**

公開中の道が **1 万本を超えたあたりで測り直す**。測り方は以下。

```
cd ~/Zekkei-touring/tools/supabase && source ~/.zekkei_supabase
python3 20260905_db_admin.py sql "select count(*) from public.zekkei_roads where status = 'published'"
python3 20260905_db_admin.py sql "explain (analyze) select * from public.nearby_roads(36.0, 138.0, 400000, 220, 'scenery')"
```

半径 400km・220 本が、距離計算が走るなかで最も重くなりうる条件。
1 秒を超えるようであれば、次の手を検討する。考えられる対応は、
縮尺に応じて本数の上限を下げる、地域ごとに代表的な道を事前に選んでおく、
距離の条件を矩形での絞り込みに変えるなど。

**教訓**

並べ替えの条件を変えるときは、索引が使えなくなっていないかを確認する。
今回は機能としては正しく動いていたため、利用者からの報告まで気づけなかった。
